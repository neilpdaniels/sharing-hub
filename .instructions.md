# Sharing Hub Python Coding Instructions

## Scope
Apply to: `**/*.py`

## Naming Conventions

- Use snake_case for variables and functions
- Use PascalCase for class names  
- Use UPPERCASE for constants

## Code Style

- Follow PEP 8 style guidelines
- Limit line length to 88 characters (Black formatter standard)
- Use type hints for function signatures where practical

## Best Practices

### String Formatting
- Prefer f-strings for string formatting over `.format()` or string concatenation

### Collections
- Use list comprehensions for simple transformations
- Use dictionary comprehensions for mapping operations

### Resource Management
- Use context managers (`with` statements) for resource management:

```python
# ❌ Avoid
file = open('data.txt')
content = file.read()
file.close()

# ✅ Prefer
with open('data.txt') as file:
    content = file.read()
```

## Django-Specific Guidelines

### Celery & Async Tasks

**Critical rule:** Use Celery tasks for any operation that would block the request/response cycle.

Blocking operations include but are not limited to:
- Email sending (`send_mail()`, `EmailMessage.send()`)
- Image processing (resizing, format conversion, thumbnails)
- External API calls (requests, geocoding lookups, payment processing)
- Heavy database operations (large bulk updates, complex aggregations)
- File processing (PDF generation, document conversion)

Pattern for moving blocking code to Celery:

```python
# ✅ Create an async task
from celery import shared_task

@shared_task
def send_verification_email(email, code):
    """Send email asynchronously."""
    send_mail(subject=..., message=..., recipient_list=[email])

# ✅ Queue the task instead of calling directly
send_verification_email.delay(email, code)
```

**Exception:** Fast database lookups, validation, and synchronous response logic are not blocking and should remain synchronous.

### Celery Logging Standards

- Log task start at `debug` with key identifiers (task name, object id, user id, transaction reference).
- Log successful completion at `debug` with outcome summary and elapsed time.
- On failure, log business context at `info` (inputs, ids, non-sensitive state) before raising/logging the exception.
- Log stack traces at `exception` (or `error` with `exc_info=True`) so failures are diagnosable.
- For tasks with retries, emit a `warning` when failures repeat (for example when `self.request.retries >= 2`).
- Never log secrets, tokens, full card data, or full PII; log only masked identifiers.

Pattern for retries with repeated-failure warning:

```python
@shared_task(bind=True, autoretry_for=(Exception,), retry_backoff=True, max_retries=5)
def example_task(self, obj_id):
    start = timezone.now()
    logger.debug("example_task started", extra={"obj_id": obj_id})
    try:
        # ... task work ...
        logger.debug(
            "example_task completed",
            extra={"obj_id": obj_id, "elapsed_ms": int((timezone.now() - start).total_seconds() * 1000)},
        )
    except Exception:
        logger.info("example_task failed", extra={"obj_id": obj_id, "retry": self.request.retries})
        if self.request.retries >= 2:
            logger.warning("example_task repeated failures", extra={"obj_id": obj_id, "retry": self.request.retries})
        logger.exception("example_task exception", extra={"obj_id": obj_id})
        raise

    ### Task Idempotency

    - All Celery tasks that change payment, transaction, or status state must be idempotent.
    - Guard against duplicate execution using terminal-state checks and unique external references.
    - Safe re-run rule: calling the same task twice must not double-charge, double-capture, or duplicate side effects.

    ### Atomic State Transitions

    - Use `transaction.atomic()` for multi-step status changes that must stay consistent.
    - Use `select_for_update()` where webhook/task/polling races are possible.
    - Persist state transitions in a single transactional unit where feasible.

    ### Retry Policy Standards

    - For network-bound tasks, define retries explicitly with `retry_backoff` and `max_retries`.
    - Retry transient failures only (timeouts, connection errors, upstream 5xx).
    - Do not retry validation or business-rule failures.
    - Log retry attempt counts on each failure path.

    ### External API Contract

    - Every outbound HTTP call must specify an explicit timeout.
    - Log provider, endpoint/action, status code, and latency (without secrets).
    - Return user-safe error messages; keep sensitive diagnostics in server logs only.
    - Keep request timeout budgets short enough to avoid long request blocking.

    ### Observability and Correlation

    - Propagate and log correlation identifiers across views, tasks, and webhooks.
    - Preferred ids include: `transaction_reference`, `setup_intent_id`, `task_id`, and `user_id`.
    - Log records for a single flow should be traceable end-to-end with shared identifiers.

    ### Sensitive Data Redaction

    - Never log card PAN, CVC, full Stripe secrets, authorization headers, or client secrets.
    - Never log full emails in warning/error paths; mask local parts when possible.
    - Log only minimal identifiers required for debugging.

    ### Testing Expectations for Async and Payment Flows

    - Add tests for success paths, retry paths, and hard-failure paths.
    - Add tests for repeated-failure warning behavior.
    - Add idempotency tests (duplicate task/webhook invocation).
    - Add race-condition tests for overlapping updates from webhook/task/UI polling.

    ### Rollout Safety for Behavior Changes

    - For payment/status logic changes, prefer staged rollout or feature flags when feasible.
    - Document migration/backfill requirements when introducing new statuses.
    - Include rollback/fallback notes in PR descriptions for high-risk behavior changes.

### Views & Responses

- Keep view logic focused on request handling and response generation
- Defer heavy lifting to Celery tasks
- Return responses immediately; let tasks complete in background
- Use task status endpoints or AJAX polling for user feedback on async operations

### Image Processing

Image processing should always be deferred to Celery:

```python
# ✅ Save the object first, then queue async processing
obj.save()
process_image_task.delay(obj.id)  # Run in background
```

Never process images synchronously in `save()` methods or view handlers. Users should get immediate feedback while images are resized/optimized in the background.

## Imports

- Group imports: standard library, third-party, local
- Keep import lists organized and remove unused imports
- Use absolute imports within Django apps

## Comments & Documentation

- Write docstrings for all functions, classes, and tasks
- Use docstrings to explain the "why", not just the "what"
- For Celery tasks, note what blocking operations they perform

## Error Handling

- Use try/except blocks appropriately but don't suppress errors silently
- In Celery tasks, log exceptions thoroughly for debugging
- Return meaningful error states (don't just fail silently)
