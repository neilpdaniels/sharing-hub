# Video upload, previews and downloads

Video evidence and message attachments use two stored versions:

- **Uploaded video:** compressed on the device before upload, targeting up to 1080p/30 fps with audio. This file is preserved byte-for-byte on the server and is the full-quality download.
- **Preview:** generated by a Celery worker as H.264/AAC MP4, fitting inside 854×480 (landscape) or 480×854 (portrait), 24 fps, CRF 28, capped at 1.2 Mbps video and 64 Kbps audio. Small videos are not upscaled.

The existing `video` and `video_raw` fields point to the same uploaded file for new uploads; `video_preview` points to the smaller derivative. Existing duplicate archives are retained. We do not replace or recompress the uploaded evidence on the server.

The app uses native compression on Android/iOS. The website uses a locally bundled Mediabunny/WebCodecs worker, targeting 6 Mbps video and 128 Kbps audio. It selects MP4/H.264/AAC where supported, otherwise WebM/VP9/Opus. This requires HTTPS (or localhost) and browser support for decoding the selected video's codecs. Unsupported codecs fail visibly rather than dropping audio/video tracks or uploading an uncompressed file. The original device recording remains untouched. The compressed upload limit is 50 MiB.

Both participants can watch the smaller preview or download the full uploaded file. Preview processing failures do not remove the upload or block its download. External video URLs remain external: the server does not download or transcode them.

## Deployment

1. Apply the schema: `python manage.py migrate` with the deployment's usual settings.
2. Install FFmpeg in the worker environment. The Docker image now includes it. For non-Docker environments, install `ffmpeg` or set `FFMPEG_BINARY` to an executable path.
3. Ensure the web process and worker share the same database, media storage, Django settings and Celery broker.
4. Run a dedicated worker: `celery -A rentalution worker -Q video --loglevel=info --concurrency=2`. Set `DJANGO_SETTINGS_MODULE` to the same settings as the web process. The compose configuration includes a `video-worker` service and Redis.
5. Collect static files and build/install the updated mobile app.
6. Queue existing uploaded videos: `python manage.py process_video_previews`. This only enqueues Celery jobs; it does not encode inside the management/web process.

To retry failed previews, run `python manage.py process_video_previews --retry-failed`. This also recovers processing records older than 15 minutes. The encoder has a five-minute timeout. Celery queues new files only after their database transaction commits. Preview publishing deliberately bypasses local eager mode; a real worker and broker are required even when other local tasks run inline. It uses a separate `video` queue so encoding does not occupy payment-task workers. If queue submission fails, the full upload is retained and preview status is marked failed for retry.

Downloads use signed, one-hour links issued on participant-facing pages/API responses and `Content-Disposition: attachment`. Refresh the transaction to renew an expired link. Existing media serving policy is unchanged.

## Browser bundle and checks

The built browser worker is committed under `transaction/static/transaction/`, so production does not need Node. To rebuild it:

```sh
cd transaction/video_client
npm ci
npm run build
```

Keep `mediabunny.LICENSE.txt` (MPL-2.0) with the bundle. The unmodified library source is available in the pinned [Mediabunny 1.56.2 package](https://registry.npmjs.org/mediabunny/-/mediabunny-1.56.2.tgz); `package-lock.json` records its integrity hash. [Mediabunny conversion documentation](https://mediabunny.dev/guide/converting-media-files) describes the worker conversion API.

Run `python manage.py test transaction.test_video_previews mobile_api.test_workflow_parity` with the usual test settings; set `FFMPEG_BINARY` if necessary. The real encoder test checks portrait/landscape dimensions, audio, smaller output, download integrity and failure behavior.

The optional `scripts/test_video_upload_browser.py` check requires Playwright/Chromium and FFmpeg. It compresses generated portrait/landscape WebM/Opus clips and an MP4/H.264/AAC clip in an actual browser worker and checks frame count, audio amplitude and output size. Browser codec availability differs; the MP4 case also accepts an explicit unsupported-codec error when that decoder is unavailable.
